# 2026-11-21 · Rerank 重排：检索的第二道工序

RAG 检索链路讲了召回（余弦相似度），今天补第二道工序：重排（rerank）。

## 为什么召回之后还要重排

向量召回用的是 **bi-encoder**（双编码器）：问题和文档**分别**编码成向量再比相似度——快，可以用索引从百万文档里毫秒级捞出 top-50，但精度有限，因为两段文本互相"没见过面"。

重排用的是 **cross-encoder**（交叉编码器）：把问题和候选文档**拼在一起**送进模型统一打分——两段文本充分交互，判断"这段到底能不能回答这个问题"精准得多；但慢，无法全库跑，只能对召回出来的几十条逐一打分。

## 流水线分工

```
全库 100 万条 → 向量召回（快而粗）→ top 50
             → rerank 精排（慢而准）→ top 5 → 拼进 prompt
```

**先粗后精**，速度和精度兼得——和"初筛简历→面试细聊"是一个道理。

## 工程要点

- rerank 模型可选：bge-reranker、Cohere Rerank、智谱等都有现成 API
- 成本控制：只重排 top 30~100，不要全量
- 我的 rag-backend 目前是召回直通生成，加 rerank 是明确的升级路线——面试聊到"检索不准怎么优化"时，这是最有分量的一板斧。

## 面试一句话

> 召回负责"从海里快速捞网"，用双编码器牺牲精度换速度；重排负责"网里精挑"，用交叉编码器对少量候选逐一深评——先粗后精，是检索系统标准的两级流水线。
