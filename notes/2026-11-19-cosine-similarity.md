# 2026-11-19 · 余弦相似度：向量检索的心脏

RAG 链路讲完了切分和 SSE，今天补检索侧最核心的一个概念：为什么"语义相近"能被算出来。

## 从文本到向量

embedding 模型把一段文本压成一个高维向量（比如 1024 维）。关键性质：**语义越接近的文本，向量方向越接近**。"猫咖怎么收费"和"门店价格"字面几乎不重合，但向量夹角很小。

## 余弦相似度是什么

只看两个向量的**夹角**，不看长度：

```ts
function cosineSim(a: number[], b: number[]): number {
  let dot = 0, na = 0, nb = 0;
  for (let i = 0; i < a.length; i++) {
    dot += a[i] * b[i];      // 点积
    na += a[i] * a[i];       // |a|²
    nb += b[i] * b[i];       // |b|²
  }
  return dot / (Math.sqrt(na) * Math.sqrt(nb));
}
```

结果 ∈ [-1, 1]：1 = 方向相同（最相似），0 = 无关。**为什么不用欧氏距离？** 文本长短会影响向量长度，但语义不该被长度干扰——余弦只看方向，天然免疫长短差异。

## 在 RAG 里的位置

用户问题 → embedding → 和库里所有 chunk 向量逐一算余弦 → 按分数取 top-k → 拼进 prompt。我的 rag-backend 走的就是这条标准链路；工程上向量库（如 FAISS/milvus）做的事就是把"逐一比较"优化成索引加速。

## 面试一句话

> 语义检索的本质是把"意思像不像"转化为"向量夹角小不小"，余弦相似度只看方向不看长度，所以不受文本长短影响；检索就是问题向量与全库 chunk 向量算相似度取 top-k。
